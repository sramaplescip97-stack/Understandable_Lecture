# 運用ルール（最小構成）

討論（タイムライン「開発環境の設定」）の合意を、運用できる形に落としたもの。

## 状態遷移

```
idea Issue ──ゆきか承認──> task Issue (status:ready)
task Issue ──計画検証OK──> status:ready のまま着手可
着手 ──> status:in-progress ──PR作成──> レビュー待ち
CI緑＋PR検証OK ──> ゆきか確認 ──> マージ ──> status:done
失敗 ──> try を進める（上限3回）。上限到達／例外 ──> status:needs-human で停止し、進行役が要約してゆきかへ
関門に触れる ──> gate:needs-approval を付けて承認まで進めない
```

## 停止条件（初日から固定）

- 1ジョブ **30分** で打ち切り（workflow の timeout）
- 同一タスクの多重起動はしない（concurrency で直列化）
- 試行は **3回まで**。失敗のたびに Issue の「試行記録」に理由を1行残し、try ラベルを進める
- CI が **2回連続で赤** になったら、3回目を待たずに人へ回してよい
- コストは API 側の月額アラート＋上記の時間・試行上限で抑える

## 検証の分担

- 計画段階（Issue）：ChatGPT が曖昧さ・受け入れ条件の不足・テスト観点を指摘する
- PR段階：Gemini が仕様・型定義・関連モジュール・CIログを突合する広域QA（仮置き。同一PR比較試行で確定）
- CI（機械判定）が赤の PR は、どちらの検証にも上げない
- **実装者は受け入れテストを改変できない**。テストが間違っていると思う場合は、直さずに Issue で人へ上げる

## 役割の境界

- 計画分解（Opus 等のセッション型LLM）の出力は、ゆきかの承認を経て初めて有効な計画になる
- 新機能提案は呼ばれた時だけ動く。出力先は idea Issue のみ
- 「管理者が承認したからマージ」は禁止。マージ承認は常時ゆきか

## 人間の関門（承認なしに進めない）

- 要件の確定・計画の承認
- main へのマージ、本番デプロイ
- DB スキーマ等の破壊的変更、依存の追加
- 課金・秘密情報・データ削除・外部公開

## 巻き戻し

- コードは PR 単位で revert できる形を保つ（1PR＝1つの変化）
- 戻せない操作（DB マイグレーション、外部送信等）は関門側に置き、自動実行させない
